codelesstraveled.com
====================

Plain HTML, CSS and JS. No build step, no dependencies, no
node_modules — which is also the argument the site makes, so it had
better be true here. Upload the folder; that's the deploy.

  index.html        the page (contours are inlined into it)
  styles.css        palette and layout live in :root at the top
  main.js           draws the l of "less" as the fork
  tools/contours.py regenerates the terrain
  shots/            project screenshots
  favicon.svg       the mark
  contours.svg      last generated terrain, for reference

Open index.html in a browser to work on it.

THE IDEA
--------
The page is a survey sheet. Contours run edge to edge at full
strength and the writing sits on translucent overlay sheets laid
over them. That is a drafting convention rather than a UI one:
tracing paper or mylar over a survey, so you can write on it
without losing the ground underneath. The inset highlight along the
top edge of each sheet and the low soft shadow are what make it
read as paper rather than as glass — remove them and it becomes a
frosted rectangle.

The route line down the left is the spine of the layout and the
metaphor at the same time. Stop 01 is where the reader is. Stop 05
is where they're going. Nobody needs that explained, which is the
point: it is more legible to a non-designer, not less.

THE TERRAIN
-----------
Real contours, not a texture. tools/contours.py builds a height
field from six gaussian hills plus two sine ridges, traces isolines
through it with marching squares, chains the loose segments into
polylines, and writes the result into index.html between the
CONTOURS markers.

    python3 tools/contours.py

Move the hills, change LEVELS, rerun. Every fifth contour prints
heavier, the way an index contour does on a real sheet.

It is inlined rather than loaded as an <img> because the strokes use
currentColor — the CSS decides what colour the land prints in, and
an external file could not take part in that.

THE STRIP MAP
-------------
A strip map is a real object: a long thin map of a route and nothing
either side of it, carried by walkers and printed in trail guides.
That is what runs down the right-hand side.

Generated by tools/minimap.py — the same marching-squares code as the
background, on a smaller field, plus a route that wanders. The wander
matters: a straight line would read as a loading bar.

main.js places the marker with getPointAtLength, so it sits exactly on
the line however that line bends. Nothing approximates the curve, and
nothing has to be kept in step with the generator by hand. Each
waypoint is placed the same way, at the fraction of the page its stop
actually occupies, and each is a real link to that stop — so this is
wayfinding, not ornament.

Hidden below 62rem. There is no room beside the content on a narrow
screen, and the rail down the page already does the job there.

WHY NOT PAN THE WHOLE BACKGROUND
--------------------------------
It was considered, and the performance objection is not the real one:
the vellum sheets already re-rasterise their blur on every scroll
frame, because they move over a fixed background. Panning the terrain
adds very little on top of a cost already being paid.

The objection is motion sickness. A background that pans and rotates
under fixed panels is the pattern that triggers it, and it fights the
stillness that makes the sheets work.

So the land drifts instead, and only slightly: 90px sideways, 130px
up, and 1.6 degrees of tilt across the entire page, on two different
periods so it wanders rather than slides. Transform only, so it
composites on the GPU. DRIFT_X, DRIFT_Y and DRIFT_R at the top of that
function in main.js are the knobs — push them and you will find the
point where it stops being pleasant quite quickly.

Anyone who has asked their OS for reduced motion gets none of it.

THE MARKER
----------
The route is dotted for ground not yet covered and inked in for
ground behind you, with a position dot on the line and each waypoint
filling in as it is passed. That is how a map shows a walked route,
and it doubles as a scroll indicator without looking like one.

The reference point is 45% up the viewport rather than its top edge,
so the marker sits roughly where a reader is looking. Scroll handling
is throttled through requestAnimationFrame and registered passive.

All of it is aria-hidden and none of it is required: with the script
absent the route is a plain solid line, exactly as before.

THE FORK, AND WHY IT WAS TOO HEAVY
----------------------------------
Three separate faults, all in the measuring:

  - The weight was read from font-weight, which computes to 400 here.
    The title renders at 800 through the variable axis, so the canvas
    was measuring the wrong master. It now reads wght out of
    font-variation-settings.

  - The stem came from TextMetrics.actualBoundingBoxLeft/Right, and
    engines disagree about whether those describe the ink or the
    advance box. Where an engine returns the advance, the stem comes
    back nearly as wide as the letter. It is now found by rasterising
    the glyph and counting pixels, which cannot be misread. There is
    a sanity clamp too: a stem outside 6-22% of an em is rejected and
    the plain letter is left alone.

  - The fork joined with a miter. Between a vertical and a shallow
    diagonal that throws a long spike, and the spike was most of the
    apparent bulk. It is a round join now.

--fork-weight (0.86) trims it optically on top of all that. A
diagonal at the same width as a vertical always looks heavier than it
measures; type designers cut them thinner for the same reason. Raise
it toward 1.0 for a heavier mark.

READABILITY
-----------
Measured, not eyeballed. Against a dense band of index contours the
overlay at 0.62 alpha puts body text at 7.9:1, so the sheet can stay
genuinely translucent instead of nearly opaque. --soft is #474339,
which clears 4.5:1 even directly over a contour line.

Two fallbacks are wired in:
  - browsers without backdrop-filter get a 0.94-alpha sheet
  - anyone who has asked their OS for reduced transparency gets a
    fully opaque one

PERFORMANCE — READ THIS ONE
---------------------------
backdrop-filter over a large fixed SVG is by far the most expensive
thing on this page. It is the one part that could stutter while
scrolling on an older phone. Test on the cheapest device you own
before this goes live. If it struggles, the fix is one line: drop
--blur to 0 and raise the --vellum alpha to about 0.9, which gets
you the panels treatment instead and costs nothing.

TWO FIXES APPLIED
-----------------
This is the build whose minimap you said worked. The minimap itself
was not touched: its route, its marker, and the code that drives them
are as you sent them.

1. THE LAND HOLDS STILL. DRIFT_X, DRIFT_Y and DRIFT_R in main.js are
   now 0, so the background no longer moves independently of the
   content. The code path is still there — raise them above zero to
   bring it back, though anything past about 30 and half a degree
   gets unpleasant quickly.

2. THE TRAIL REACHES ITS END. Progress is now the plain scroll
   fraction: 0 at the top, 1 at the bottom, by definition.

   It used to be how far a reading line had travelled through the
   route element, which could never reach 1, because at maximum
   scroll the route still sits below that line. The unreachable
   remainder ran from 5% to 16% depending on viewport height and
   page length, which is why it looked inconsistent.

   This needed three changes, not one — waypoint placement, progress,
   and passed-state all used the old measure, and moving one without
   the others would have left them disagreeing. All three now run off
   the same number, so the marker and the filled waypoints agree by
   construction rather than by coincidence. The terminus bar at the
   foot of the rail inks red on arrival.
